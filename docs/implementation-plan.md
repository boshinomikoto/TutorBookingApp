# План реалізації v1.0

Шари `Models`/`Data`/`Services` вже створені в ЛР №1–2: сутності `Student`,
`Consultation`, `ConsultationStatus`, і бізнес-правило перевірки перетину
часу в `ConsultationService`. План нижче впорядковує те, що з цієї
специфікації ще потрібно систематично довести до повної відповідності
й перевірити в ЛР №4 — послідовність спирається на залежності між
сценаріями, а не є простим списком.

1. **Учень — базова сутність** (FR-01, FR-02 / UC-01, UC-02). Без
   зареєстрованого учня неможливо створити запис на консультацію —
   `Consultation.StudentId` посилається на вже існуючого `Student`.
2. **Створення запису і перевірка перетину часу** (FR-03, FR-04 / UC-03).
   Центральне бізнес-правило v1.0; усі інші операції над записом
   (скасування, завершення, перегляд) працюють з уже створеними
   записами.
3. **Скасування і завершення запису** (FR-05, FR-06 / UC-04, UC-05).
   Обидва сценарії залежать від існування запису зі статусом Scheduled і
   переводять його в кінцевий стан (`State Machine Diagram`, `design.md`).
4. **Перегляд розкладу та історії** (FR-07, FR-08 / UC-06, UC-07).
   Суто читання вже накопичених даних, тому розміщені останніми в
   послідовності — коректні лише коли попередні кроки видають правильні
   статуси записів.
5. **Перевірка нефункціональних вимог** (NFR-01–NFR-03) — проводиться
   паралельно з кроками 1–4: локальність і відсутність мережі
   перевіряються архітектурно, час відгуку (NFR-02) — вимірюванням на
   референсному наборі даних у ЛР №4.

Кожен крок переходить від погодженої в цьому документі baseline вимог до
коду і тестів лише після `git tag requirements-baseline-v1.0` — зміни
вимог після цього тега вимагають явної повторної процедури узгодження,
а не прямого редагування `requirements.md`.
